## Research and evidence

Источники: текущий `origin/master`; официальная документация https://docs.maxma.com/api/ и её https://api.maxma.com/openapi.yaml (версия `2025-Nov-13`, повторно получена 20.11.2026); локальный CS-Cart core в `/var/www/html` как справочник контрактов hooks и RMA. Версия целевого магазина пока не подтверждена.

| Приоритет | Подтверждение в master | Следствие |
| --- | --- | --- |
| P0 | `SetOrderRequestBuilder::build()` вызывает `setRedPrice(... ?? 0)` даже без акционной цены; прямой вызов builder дал `0` | В MAXMA передаётся нулевая акционная цена; по API переданный `redPrice` заменяет `blackPrice` |
| P0 | `calculationToArray()` приводит денежные скидки к int; воспроизведено `12.75 → 12` | Потеря копеек |
| P0 | `applyExternalBonuses()` сравнивает ключ массива с `(string)$key` строго; для ID `100` воспроизведена скидка товара `0` | Числовой ключ строки не сопоставляется с товаром |
| P0 | API-ошибка возвращает `[]`, coupon hook передаёт его в метод с аргументом `object`; cached array передаётся в `handleCalculationResult(V2CalculatePurchaseResponse ...)` | Оба случая воспроизведены как TypeError |
| P0 | `QueueService::processItem()` проглатывает ProcessingException; после успешного fallback updateClient всё равно выполняется `throw $e`; неизвестный метод оставляет processing | Ложный успех обработки, ошибочное состояние и зависшие задания |
| P0 | RMA payload перезаписывается в цикле, add вызывается после цикла; refund складывает только price, DTO хранит сумму как int | Теряются отдельные возвраты, количество и дробная часть суммы |
| P1 | `saveUserBonusesData()` сохраняет штатные баллы только при `!empty(balance)` | Успешный ответ с нулевым балансом не обнуляет старое значение |
| P1 | `UserSession` хранит balance/history без user_id; `get_user_info` передаёт auth текущей сессии для произвольного пользователя | Риск подстановки кеша другого пользователя при последовательном чтении профилей |
| P1 | `get_user_info` handler требует int profile_id; core вызывает hook и при `fn_get_user_info(id, false)` с null; прямой вызов воспроизвёл TypeError | Сбой обычного чтения пользователя без профиля |
| P1 | Повторный расчёт использует старый массив, если total_discount > 0, без проверки состава корзины | Состояние скидки может пережить изменение товаров/количества/баллов |

Дополнительные границы доказательств:

- Прямые воспроизведения выполнены без сети MAXMA и без записи в БД, через существующие SDK models и методы модуля.
- PHP 8.3 lint: 36 собственных PHP-файлов, 0 синтаксических ошибок. Это не подтверждает работоспособность интеграции.
- В `master` `idx_type_entity` НЕ unique; нельзя переносить предположения о дедупликации из другой копии.
- В проверенном локальном CS-Cart `db_replace_into()` реализован через upsert с обновлением переданных полей. Потеря balance при записи history НЕ считается подтверждённым дефектом; сохранность обоих полей проверить регрессией на целевой версии.
- `UserSession` в master корректно сохраняет переданную ссылку. Исправлять отсутствующее свойство по старой копии здесь не нужно.
- Отдельная `7.4php` содержит другой SQL, включая DROP TABLE; эти изменения в план не переносить.

## Assumptions and blockers

- План опирается на default branch `master`; портирование на PHP 7.4 — отдельный объём.
- В репозитории нет своих тестов, root Composer, PHPStan/Psalm configs и окружения CS-Cart.
- На хосте доступны PHP 8.3, PHPStan 1.12.34 и Psalm 4.30.0; Composer и PHPUnit в PATH отсутствуют. Установку dev-зависимостей выполнить в задаче 0 до изменения PHP; сейчас она не требуется.
- Для полного DEV-приёмочного прогона нужны версия CS-Cart, изолированная копия магазина/БД, reward_points и RMA, тестовые реквизиты MAXMA. Без них не объявлять live-обмен проверенным.
- Семантику возвратной цены после скидок и налогов подтвердить на RMA целевой версии: сумма должна соответствовать возвращаемой стоимости, а не текущему каталожному прайсу.

## Review Focus

1. Отсутствующая акционная цена, денежные значения с копейками, количество > 1 — согласованные расчёт, payload заказа и итог CS-Cart.
2. Отказ MAXMA, timeout и старый cached array — контролируемая ошибка без TypeError и без применения устаревшей скидки.
3. Повторный статус, несколько RMA одного заказа и неизвестный исход сетевого запроса — отсутствие слепого повторного финансового вызова.
4. Валидный баланс 0, отсутствие ответа, два разных пользователя в одной сессии — ноль сохраняется только по успешным данным, кеш не смешивается.
5. Nullable profile_id и работа без RMA — существующие CS-Cart сценарии не падают из-за сигнатур или необязательного add-on.

## Database migration and deployment plan

- Required: NO в запланированном объёме; новые таблицы, столбцы и индексы не добавляются. Состояния очереди и её текущая схема сохраняются.
- Совместимость старой очереди обеспечивается чтением существующих payload; старые финансовые ERROR/PROCESSING не переотправляются автоматически.
- Перед DEV проверить исходную схему; она может отличаться у клиента от master. При необходимости DDL или массового преобразования данных сначала дополнить план отдельной миграцией и деплоем. Runtime-DDL запрещён.
- Удаление/переустановка add-on не является процедурой обновления: uninstall удаляет `orders.maxma_promotion_data`; install содержит неидемпотентные CREATE/ALTER. Не запускать их над существующими данными ради исправления кода.
- Перед будущим выкладыванием сохранить код, настройки и БД с очередью. Развёртывание/публикация не разрешены текущим запросом.

## Regression plan

- Unit-регрессии перечислены в задачах 1–5; использовать реальные SDK models и подменять только инфраструктуру. Не строить универсальный тестовый фреймворк или матрицу всех методов MAXMA.
- DEV с БД: balance/history сохраняются независимо; два RMA сохраняются отдельными операциями; повторная обработка и два обработчика не дают второй отправки одной занятой записи; исходная очередь и настройки сохранены.
- DEV в браузере: профиль с нулевым балансом; корзина с копейками и qty>1; корректный/некорректный купон; изменение/удаление купона; обычное оформление; set→confirm, set→cancel и confirm→return; админка показывает частичный отказ очереди как ошибку.
- Для браузерных сценариев использовать Playwright и проектный wrapper, если он есть. Для реального обмена только тестовый MAXMA аккаунт и test mode.
